Module 0 · Step 1 · Start from zero

How a computer remembers things

Before we touch anything called "DSA", you need three small ideas. That's all. Each one is something you already understand from daily life.

Idea 1 · A program A program is just a list of instructions, written in order, that the computer follows one by one. Like a recipe. Nothing more.
Idea 2 · Memory A computer's memory is like a school corridor with millions of small lockers. Every locker has a number painted on it. Each locker can hold one small thing — like one number.
Idea 3 · A variable A variable is one locker that you put a name sticker on. Instead of remembering "locker number 7,204,158", you just say age, and the computer finds that locker for you.

Try it. This is a real working variable:

Your first variable · try it yourself
The computer will store your number in one locker and stick the name "age" on it.

That's it. You now know what a variable is: one named locker holding one value.

One locker, one name, one value. Remember that — because now we're going to break it.

Step 2 · The story

The day one-locker-one-name stopped working

It's around 1955. Computers are new. The only tool programmers have is the variable — the named locker you just used.

Your school gives you a job: store the exam marks of 10,000 students.

You only know variables. What would you do? Pick whatever feels natural — there is no wrong answer.

Ugly, but it works… as long as you always know which variable you want while writing the program.

Then a teacher walks up to your computer and types a number: 8437. She wants the 8,437th student's mark. Right now.

Important: you wrote the program yesterday. The number 8437 arrived today, from the teacher's keyboard. Tomorrow she might type 212. Your program must handle any number. How do you print that student's mark?

The wallThat only works because you typed 8437 into the code yourself. But the teacher types the number after the program is already written and running. Tomorrow she types 212 — and your code still says marks8437. A program can't rewrite itself for every new request.
The wallBrilliant instinct — and this is the thing programming languages simply don't allow. "marks" + n makes a piece of text, like writing "marks8437" on paper. A name sticker and a piece of paper that looks like a name sticker are not the same thing. The computer can't find a locker using text you invented while running.
The wallPainfully honest — and people basically did this! But now your program is 10,000 lines of "if". Next year there are 40,000 students. You'd spend your life copy-pasting if-lines. There has to be a better way.

Feel the wall? You have 10,000 values, and no way to say "give me student number n."

All three plans failed for the same deep reason: a variable's name is not a number. You can't do maths with a name. But the teacher gave you a number. What you need is a container where the number itself finds the value.

Step 3 · The invention

The array: let the number be the name

Here's the invention, and it's beautifully simple.

Instead of 10,000 lockers scattered all over the corridor with 10,000 name stickers, you go to the school office and say: "Give me 10,000 lockers in one straight row, side by side, no gaps."

Say your row starts at locker number 5000. Then:

The whole trick
student 1's mark → locker 5000
student 2's mark → locker 5001
student 3's mark → locker 5002
…
student n's mark → locker 5000 + n − 1
The teacher types 8437 → the computer calculates 5000 + 8436 = locker 13436 → opens exactly that locker. One small sum. Done.

No name stickers. No searching. The position of a student became the way to find them. That container — a row of lockers side by side, found by position — is called an array.

New word · Array A row of memory lockers, side by side, holding values of the same kind. You get any value instantly by giving its position number.
A little historyThis wasn't invented in a classroom. In the 1950s, programmers were doing this locker maths by hand, and it was slow and painful. In 1957 a language called Fortran finally said: "just write marks(8437) and I'll do the maths for you." That was the moment the array became part of programming. It was born from real pain, not theory.
New word · Index The position number you use to open an array's locker. One catch: computers count positions starting from 0, not 1. So the first mark is marks[0] and the 8,437th mark is marks[8436]. Why start at 0? Because the index is really "how many steps from the start" — and the first locker is 0 steps away.

Try position 3, then position 9999. Jumping takes the same tiny effort every time, no matter how far. Walking gets worse the further you go.
New words · O(1) and O(n) Programmers have nicknames for what you just saw. "Same effort no matter how big" is called O(1) (say: "oh-one"). "Effort grows as the data grows" is called O(n) (say: "oh-en" — n means the number of items). That's all these scary symbols mean. Array jump = O(1). Walking = O(n). You now read your first complexity notation.

A free gift: neighbours come along

One more real thing, made simple. Main memory is far from the computer's brain, like lockers in another building. So when the computer fetches one locker, it photocopies the whole shelf — about 16 lockers — onto a small desk right next to its brain. That desk is called the cache (say: "cash"). Click any locker below:

One shelf of 16 marks · click any locker to read it
Read one mark, and the 15 next to it land on the desk for free. So a loop reading an array flies — the next value is almost always already on the desk.

This only works because array values are neighbours. If your 10,000 values were scattered all over the building, every single read would be another long trip. Keep this in your pocket — it becomes very important when we meet linked lists.

Optional depth · press "why?" as many times as you like

Still curious? Keep asking why

Every line below is true. Press why? to open the reason. Some reasons have their own why? inside. Go as deep as you feel like — each level is written just as simply. If you keep pressing, you'll quietly end up learning how the machine itself is built.

The lockers must be side by side, with no gaps.

The magic sum "5000 + position" only works if every locker is exactly one step from the previous one. If locker 3 could be anywhere in the building, no sum could find it — you'd need a notebook listing where each one went.

So why not just keep that notebook?

Think about what the notebook is: a numbered list where you need to jump to entry n instantly… that's an array again! The escape plan turns out to be the same thing you were escaping. So "side by side" is where the chain stops.

Any locker takes the same time to open, near or far.

Because memory is not a corridor you walk through. It's more like a telephone system: give the number, and the wiring connects you straight to that one locker. Locker 14,999 answers as fast as locker 5,000.

Why is memory wired like a telephone system?

Inside the memory chip there's a circuit called an address decoder. It takes the locker number and electrically switches on exactly that one row — like dialling a number rings exactly one phone. No walking exists at the hardware level at all. This is why it's called RAM: Random Access Memory — "random" meaning ANY locker, equally fast.

Congratulations — you just crossed into computer architecture without noticing. This is the bottom floor.

An array can't simply grow bigger when it's full.

Your row got lockers 5000–14999. Locker 15000 may already belong to another program's data. You can't grab your neighbour's locker just because you need more space.

Then how do Python lists grow whenever they want?

They secretly cheat: when the row is full, the computer finds a longer empty row somewhere else, copies everything across, and abandons the old row. To avoid doing this often, it books roughly double the space each time. Under every "flexible" list in every language, there is a plain fixed array being replaced when it bursts.

Step 5 · Where arrays hurt

Nothing is free. Watch it break.

The array's whole power comes from one strict rule: everyone sits in position, side by side, no gaps. Now watch what that rule costs. Suppose a new value must go at the front of the row. Nobody can just "squeeze in" — every single value must shift one locker to the right first. Click and watch:

Insert 99 at the front · everyone must move
moves so far: 0
7 values → 7 moves, for ONE insertion. Imagine 10 million values, with new ones arriving every second. That's O(n) pain, over and over.

The honest list of array weaknesses:

Adding or removing in the middle

Everyone after that spot must shift. The closer to the front, the more moves. O(n).

Growing bigger

The lockers next to your row may already belong to someone else. To grow, the computer finds a longer empty row elsewhere and copies everything across. O(n) again.

Finding a value (not a position)

"Which student scored 97?" Position tells you nothing about the value inside. You must check every locker. O(n).

Reserved empty space

To avoid moving often, lists secretly rent extra empty lockers. Fast, but wasteful.

Here's the secret about all of DSA: every data structure you'll ever learn exists because the array hurt someone badly enough, in one of these exact spots, that they invented a way around it. Linked lists, stacks, queues, hash maps, trees — each one is a patch for one of these pains. That's the whole subject. It's not 50 random topics; it's one story.

Step 6 · You already use arrays every day

Where arrays hide in your daily life

Every photo on your phone

A photo is a grid of tiny colour dots (pixels) — an array of arrays. "The dot at row 800, column 600" is two little sums away.

Skipping inside a YouTube video

A video is an array of picture frames. Dragging to 12:34 = frames-per-second × seconds = a position. That instant jump is O(1) with your own eyes.

Your Spotify queue

"Play track 7" doesn't listen through tracks 1–6 first. It jumps. Position → value.

Every word you read

Text is an array of characters. The first letter of name is name[0].

Excel and marksheets

Rows and columns — arrays of arrays. "Cell C42" is locker maths, twice.

AI models

The "weights" inside ChatGPT-like models are gigantic arrays. GPUs are fast mainly because arrays sit side by side in memory.

The pattern: wherever things have a natural position and you jump straight to positions — there's an array underneath.

Coming next: the crack in the wall

You saw insertion at the front hurt. What if your data gets inserted and removed in the middle all the time, and you almost never jump to a position? The array's deal becomes exactly backwards. The fix — letting values live anywhere, each one holding the address of the next — is called a linked list, and it's Module 2. You'll arrive there already knowing why it exists.
Step 7 · Practice — only now

Think like an engineer, not an exam-taker

Three real situations. No problem says "use an array" — the hints are questions that lead your own thinking, in the exact order a senior engineer asks them. Try to answer each hint in your head before opening the next one. Code comes last because it's the easiest part.

Problem 1 · warm-up
You're building YouTube's video player. A viewer drags the red dot to 12:34 of a 3-hour video. The picture must change instantly — nobody accepts a loading circle in the middle of a drag.
Lead your own thinking
Hint 1 · what is the data?What is a video actually made of? Do those pieces have a natural order?
Hint 2 · what happens most often?In plain words, what does dragging the red dot ask the computer to do? "Jump to any…" what?
Hint 3 · what speed is demanded?"Instant, no matter where they drag" — same effort for any position. You learned a nickname for that today.
Hint 4 · what weakness disappears?Frames arrive once, in order, at the end. Nothing is ever inserted in the middle of a finished video. So which array pain simply never happens here?
Discussion

A video is an array of frames. Frames-per-second × 754 seconds = the position. One multiplication, one jump — O(1). And since finished videos never insert frames in the middle, the array's biggest weakness never fires. Data that is written once and jumped-into forever is the array's perfect customer.

// jump to any moment, instantly
frame = frames[fps * seconds]
show(frame)

Interview extra: a 3-hour video is too big for memory, so real players cut it into chunks and array-jump twice — first to the right chunk, then to the right frame inside it. The idea survives by nesting.

Problem 2 · the trap
You work at Instagram. The feed must show newest posts first. Millions of new posts arrive every hour. Your teammate says: "Simple — keep an array, put each new post at position 0." Is that a good idea?
Lead your own thinking
Hint 1 · what is the data?What's the collection here, and what order does the app promise its users?
Hint 2 · what happens most often?Two things happen non-stop. What are they?
Hint 3 · which one is expensive?You watched "insert at the front" a few minutes ago. With 10 million posts stored, what does your teammate's plan cost for EVERY single new post?
Hint 4 · question the assumptionDoes "newest shown first" really force "newest stored at position 0"? Who decided which end of the array is the front?
Hint 5 · the tradeIf you add new posts at the END (cheap — no shifting), what small thing must the reading side do differently?
Discussion

The teammate's plan shifts 10 million posts for every new arrival — O(n), millions of times an hour. The machine would spend its whole life shuffling. But "front" is just a habit, not a law. Add new posts at the end (no shifting — O(1)) and simply read the array backwards. The user sees exactly the same feed. The cost just vanishes — not with a fancy structure, but by questioning one assumption.

// writing — cheap
posts.append(new_post)
// reading — newest first, free
for i from last position down to 0:
    show(posts[i])

Interview extra: this "only ever add at the end" idea, at giant scale, is called an append-only log — it's the heart of how big systems like Kafka and databases record events. You just reasoned your way to it.

Problem 3 · the clever swap
You're building Spotify's shuffle. Every song must play exactly once, in random order, and pressing "next" must be instant — even with 10,000 songs.
Lead your own thinking
Hint 1 · what is the data?What's the collection, and what does "exactly once" forbid you from doing?
Hint 2 · try the lazy plan"Pick any random song; if it already played, pick again." Feels fine at the start. What happens when only 1 song out of 10,000 is left unplayed?
Hint 3 · find the real problemThe hard part is remembering who played. What if the array itself could keep played songs physically separate from unplayed ones?
Hint 4 · the moveYou're allowed to rearrange. What single cheap operation could push a just-played song out of the "unplayed" zone?
Hint 5 · the tradeSwapping scrambles your nice ordered playlist. Does that matter? Could you shuffle something else instead of the songs themselves?
Discussion

The lazy plan dies at the end: with one unplayed song left, you're rolling the dice ~10,000 times hoping to hit it. The elegant fix: keep all unplayed songs in positions 0 to k. Pick one at random, swap it to position k, then shrink k by one. The wall between "unplayed" and "played" is just a number. Every "next" costs exactly one swap — instant, forever.

k = number of songs - 1
when user presses next:
    r = random position from 0 to k
    swap(songs[r], songs[k])
    k = k - 1
    play songs[k + 1]

Interview extra: you just re-invented the Fisher–Yates shuffle — an algorithm most people memorize from a book. You didn't memorize it; the costs cornered you into it. That's the difference this whole course is built on. (And real players shuffle a copy of position numbers, keeping your playlist order safe.)

The road ahead

Zero to advanced: your one-month map

Here is the honest version of "DSA in one month": in 30 days of steady 2–3 hours a day, you can genuinely understand every core structure and solve interview questions with reasoning instead of memory. Real speed and hard-problem instinct keep growing after that — but the understanding, the part you care about, fits in a month. Every module will be taught exactly like this page: story first, machine second, problems last.

Week 1 How computers remember

  • Done today: memory, variables, arrays, O(1) vs O(n), cache
  • Strings (arrays of characters) and 2D arrays (grids)
  • Two little techniques born from arrays: two pointers, sliding window
  • Practice: ~15 easy array and string problems, each one reasoned the way you did today
End-of-week test: explain to someone why arr[5000] is as fast as arr[0].

Week 2 Patches for the array's pains

  • Linked lists — born where insertion hurts (you already feel this coming)
  • Stacks and queues — arrays with house rules, and why rules make things easier
  • Hash maps — the "find by value, not position" pain, solved with a genius trick
  • Practice: ~15 problems mixing all four
End-of-week test: for any task, say WHICH structure and WHY, before writing a line.

Week 3 Divide, sort, and climb

  • Recursion — a function that trusts a smaller version of itself
  • Sorting — why fast sorts are fast, not just their names
  • Binary search — the halving trick, and where it hides in real life
  • Trees — hierarchies, and why searching them is fast
  • Practice: ~15 problems
End-of-week test: explain why sorted data changes everything.

Week 4 Networks, priorities, and choices

  • Graphs — friends-of-friends, maps, the internet; walking them with BFS and DFS
  • Heaps — always knowing the biggest or smallest, cheaply
  • Dynamic programming, gently — remembering answers so you never solve twice
  • Practice: mixed interview-style scenarios, like today's Instagram and Spotify problems
End-of-month test: take a problem you've never seen and reason from data → operations → cost → structure, out loud.
