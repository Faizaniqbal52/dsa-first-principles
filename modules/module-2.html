A string was one row. But photos, game boards and spreadsheets are rows stacked into a table. The catch: memory is a single straight line. This module is about the little trick that folds a 2D table into that 1D line.

2 The story · why grids exist

Memory is a straight line. A table is not.

Every locker sits in one long hallway, numbered 0, 1, 2, 3, on and on. There is no "up" or "down" in memory. It's a single line.

Now the school wants a full marksheet: 30 students down the side, 5 subjects across the top. A table. Rows and columns.

But you only have a straight line of lockers. How do you fit a 2D table into a 1D line? Pick whatever feels natural.

Good instinctThat's the "array of arrays" idea, and it's real. In C++ it's vector<vector<int>>. But here's the twist: each of those rows is still a 1D array in a 1D memory. So underneath, the rows still have to sit somewhere on the straight line. Which leads straight to the other answer.
That's the physical truthExactly how it works underneath. Put row 0 first, then row 1 right after it, then row 2, all in one line. To reach any cell, you do a small sum. That layout is called row-major order.
Honest answerNo problem. The trick is to give up on "up and down" entirely. Lay the rows one after another in the single line, then use a sum to find any cell. Let's see it.

Say the grid has 5 columns. You store row 0 in the first 5 lockers, row 1 in the next 5, and so on:

One table · folded into one line · row by row
row 0 → lockers 0, 1, 2, 3, 4
row 1 → lockers 5, 6, 7, 8, 9
row 2 → lockers 10, 11, 12, 13, 14
…
cell (row r, col c) → locker r × 5 + c
To skip past r whole rows you skip r × 5 lockers (5 per row), then step c more to reach the column. That's the whole idea: r × cols + c.

A grid is just a 1D array with a two-part address: r × cols + c.

Look familiar? It's the array sum from Module 0, done twice: once to pick the row, once to pick the column. You already had this tool.

3 The idea · the two-part address

One formula runs the whole module: r × cols + c

Here's Module 2 in a single line: a 2D grid is a 1D array, and the address of cell (r, c) is r × cols + c.

New word · Grid (2D array) A table of values with rows and columns. Physically it's one flat array, stored row by row. In C++ you usually write it as vector<vector<int>> and reach a cell with grid[r][c].
New words · Row-major order Storing a grid one full row after another in memory. C and C++ use row-major. It's why the address is r × cols + c: each row is cols lockers wide.
Quick check
A grid has 5 columns. What flat locker holds cell (row 2, col 3)?
Nailed itSkip 2 whole rows (2 × 5 = 10 lockers), then step 3 more columns. 10 + 3 = 13. That is the entire trick of grids.
Not quite. To get past 2 full rows you skip 2 × cols lockers first, then add the column. Try the sum again.

Walking a row is fast. Walking a column is slow.

Remember the cache from Module 0? Reading one locker photocopies its whole shelf of neighbours for free. A row's cells are neighbours, so scanning a row rides that free ride. A column's cells are cols lockers apart, so every step lands on a different shelf and pays the long trip again. Same data, same loop, but row-order can be many times faster.

So should I always loop rows first, then columns?

In a row-major language like C++, yes: put the row loop on the outside and the column loop on the inside, so you move along memory in order. It's a free speed-up you get just by ordering two loops correctly.

The address is r × cols + c, not r × rows + c.

You're skipping rows, and each row is cols lockers wide. To jump past 2 rows in a 5-column grid you skip 2 × 5 lockers, not 2 × (number of rows). The multiplier is always the width of a row, which is the column count.

A colour photo is a grid where each cell is three numbers.

Each pixel needs a red, a green, and a blue value (0 to 255 each). So an image is really a grid of pixels, and each pixel is a tiny array of 3. The address maths just nests one more level: find the pixel with r × cols + c, then step to the colour you want. This is exactly how image filters and every photo app work under the hood.

5 Where it hurts · the grid costs

Grids inherit array pain, and add a direction tax

A grid is a flat array, so it carries every array weakness. Then the second dimension adds costs of its own.

Wrong-direction loops

Scanning column by column in a row-major grid fights the cache. The exact same work can run several times slower purely because of loop order.

Adding a row or column

Growing a grid means finding a bigger block and copying everything across, just like an array outgrowing its row. O(rows × cols).

Mostly-empty grids waste space

A 10,000 × 10,000 grid with a handful of real values still reserves 100 million lockers. Sparse data needs a smarter structure later.

Off-by-one at the edges

Looking at a cell's neighbours means checking you didn't fall off row 0, the last row, or either side. Forgetting an edge check is the most common grid bug.
Quick check
Two loops sum a big grid. One goes row-by-row, the other column-by-column. Same answer. Why can the column version be much slower?
ExactlyRow cells are neighbours and ride the free cache shelf. Column cells are cols lockers apart, so nearly every read is a fresh long trip to memory. Same maths, very different speed.
Think back to the cache from Module 0: reading one locker brings its neighbours for free. Which direction keeps you among neighbours? Try again.

Same bonesGrid access is O(1), a grid scan is O(rows × cols), growing is O(rows × cols), and the cache still rules. Nothing here is new. It's the array, wearing a second dimension.

7 Practice · think first

Spot the grid pattern

Three real situations. Hints are questions, not answers. Try each in your head first. Watch how often the answer is "walk the grid with two nested loops and get the index maths right".

Problem 1 · warm-up
A photo tool needs a "flip along the diagonal" button (swap rows and columns). The pixel at row r, column c should end up at row c, column r. This is a transpose.
Lead your own thinking
Hint 1 · what is the data?A grid of pixels. What two things identify one pixel, and what should swap between them?
Hint 2 · the moveIf the value at (r, c) must go to (c, r), what does the output cell (c, r) simply copy from?
Hint 3 · how do you visit every cell?What pair of loops walks every (r, c) in the grid exactly once?
Discussion

Walk every cell with two nested loops and copy: out[c][r] = in[r][c]. That's it. Cost is O(rows × cols) because you touch each cell once, and you can't do better since every value has to move. Transpose is the grid version of "just visit everything and place it where it belongs".

Problem 2 · the edges
In Minesweeper, each square shows how many of its 8 surrounding squares hold a mine. You must count a cell's mine-neighbours without crashing when the cell sits on an edge or corner.
Lead your own thinking
Hint 1 · what are the neighbours?For a cell at (r, c), what are the row and column offsets of its 8 neighbours? (Think -1, 0, +1 in each direction.)
Hint 2 · the dangerA corner cell has only 3 real neighbours. What goes wrong if you blindly read (r-1, c-1) at row 0?
Hint 3 · the guardBefore reading a neighbour, what must you check about its row and column?
Hint 4 · tidy itCould you loop the offsets -1, 0, +1 for both directions, skip the (0,0) that means "yourself", and check bounds each time?
Discussion

Loop the row offset and column offset each over -1, 0, +1. Skip the (0, 0) case (that's the cell itself). For every other offset, first check the neighbour's row is between 0 and rows-1 and its column is between 0 and cols-1, then count it if it's a mine. The bounds check is the whole problem. Grids live and die at their edges.

Problem 3 · direction and speed
A data tool sums every number in a giant grid. It's correct but slow. A colleague swears they made it 5 times faster without changing the maths at all. How?
Lead your own thinking
Hint 1 · what could change if not the maths?If the answer is identical, what about how the cells are visited could differ?
Hint 2 · recall the cacheWhich order keeps you reading neighbouring lockers: row on the outside and column inside, or the reverse?
Hint 3 · the fixThe slow version loops columns on the outside. What one swap makes every read land among neighbours?
Discussion

Same maths, different order. The slow loop walked column by column, so every read jumped cols lockers and missed the cache. Put the row loop on the outside and the column loop on the inside, and now you slide along memory in order, riding the free cache shelf. No new algorithm, just loops in the friendly order. This is one of the easiest real speed-ups you'll ever ship.

8 Now code it · C++, interview-style

Two grid problems, same five-step method

Same method as always: understand, brute force, find the waste, pseudo-code, then code and cost. The second problem reuses both transpose and the reverse you learned on strings.

Try each yourself first. Open a step only after a real attempt.

Easy · warm-upLeetCode 867 · Transpose Matrix

Return the transpose of a grid: flip it along its main diagonal so rows become columns.

Example: [[1,2,3],[4,5,6]] becomes [[1,4],[2,5],[3,6]]

Step 1 · Understand it

The value at row r, column c moves to row c, column r. If the input is R rows by C columns, the output is C rows by R columns. Edge case worth noting: the grid need not be square, so the output's shape is the input's shape flipped.

Step 2 · Brute force first

Make a fresh grid with the flipped shape (C rows, R columns). Walk every cell of the input with two nested loops and drop each value into its swapped spot. There's honestly no slower "brute force" here, because every value has to move exactly once. The only real question is getting the shape and indices right.

Step 3 · Find the shape (the only trap)

The single mistake is sizing the output. It is C rows by R columns, not R by C. Get that backwards and you index out of bounds the moment the grid isn't square. Size it right and the copy is trivial: out[c][r] = in[r][c].

Step 4 · Pseudo-code it
Pseudo-code · visit and place
R = number of rows, C = number of columns
make out with C rows and R columns
for r from 0 to R-1:
    for c from 0 to C-1:
        out[c][r] = in[r][c]
return out
Step 5 · Code it, then cost it
C++
vector<vector<int>> transpose(vector<vector<int>>& m) {
    int R = m.size(), C = m[0].size();
    vector<vector<int>> out(C, vector<int>(R));
    for (int r = 0; r < R; r++)
        for (int c = 0; c < C; c++)
            out[c][r] = m[r][c];
    return out;
}

Time: O(R × C), every cell touched once. Space: O(R × C) for the output grid.

Connects to: this "visit every cell with two nested loops" is the backbone of almost every grid problem you'll ever solve.

MediumLeetCode 48 · Rotate Image

Rotate a square grid 90 degrees clockwise, in place (no second grid).

Example: [[1,2,3],[4,5,6],[7,8,9]] becomes [[7,4,1],[8,5,2],[9,6,3]]

Step 1 · Understand it

The top row becomes the right column, the right column becomes the bottom row, and so on. The grid is square (n by n), and we may not use a second grid. So we have to rearrange the values we already have.

Step 2 · Brute force first

Make a new grid and place each value where a 90-degree rotation sends it: out[c][n-1-r] = in[r][c]. It works and it's easy to reason about. But it uses a whole second grid, and the problem said in place. So we need the same result without the extra space.

Step 3 · Find the waste (two moves you already know)

Here's the elegant part. A clockwise rotation is exactly transpose, then reverse each row. You already know both. Transpose flips across the diagonal (swap (r,c) with (c,r)), which you can do in place. Then reversing each row (two pointers, from Module 1) finishes the rotation. Two familiar moves, no second grid.

Step 4 · Pseudo-code it
Pseudo-code · transpose, then reverse rows
n = size of the grid
// transpose in place: swap across the diagonal
for r from 0 to n-1:
    for c from r+1 to n-1:
        swap grid[r][c] and grid[c][r]
// reverse each row
for r from 0 to n-1:
    reverse grid[r]
Step 5 · Code it, then cost it
C++
void rotate(vector<vector<int>>& m) {
    int n = m.size();
    for (int r = 0; r < n; r++)
        for (int c = r + 1; c < n; c++)
            swap(m[r][c], m[c][r]);      // transpose
    for (int r = 0; r < n; r++)
        reverse(m[r].begin(), m[r].end());  // reverse each row
}

Time: O(n²), each cell is touched a constant number of times. Space: O(1), all swaps happen inside the grid.

Connects to: transpose (problem 1) plus reverse-with-two-pointers (Module 1). A "hard" problem dissolves into two easy ones you already owned.
