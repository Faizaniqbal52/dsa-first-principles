2 The story · why arrays got invented

The day one locker, one name stopped working

Picture the year 1955. Computers are brand new. The only tool you have is the variable, that named locker you just tried.

Now your school hands you a job: store the exam marks of 10,000 students.

You only know variables. What would you do? Pick whatever feels natural. There's no wrong answer here.

Ugly, but it works. At least, it works as long as you already know which variable you want while writing the program.

Then a teacher walks up and types a number: 8437. She wants the 8,437th student's mark. Right now.

Here's the catch. You wrote the program yesterday. The number 8437 arrived today, from the teacher's keyboard. Tomorrow she might type 212. Your program has to handle any number. So how do you print that one student's mark?

The wallThat only works because you typed 8437 into the code yourself. But the teacher types her number after the program is written and running. Tomorrow she types 212, and your code still says marks8437. A program can't rewrite itself for every new request.
The wallGreat instinct. Sadly, this is the one thing programming languages just won't allow. "marks" + n makes a piece of text, like writing "marks8437" on paper. A name sticker and a piece of paper that looks like a name sticker are not the same thing. The computer can't open a locker using text you made up while running.
The wallPainfully honest, and people basically did do this. But now your program is 10,000 lines of "if". Next year there are 40,000 students. You'd spend your whole life copy-pasting if-lines. There has to be a better way.

Feel the wall? You have 10,000 values, and no way to say "give me student number n."

All three plans failed for the same reason: a variable's name is not a number. You can't do maths with a name. But the teacher gave you a number. What you really need is a container where the number itself finds the value.

3 The fix · meet the array

The array: let the number be the name

The fix is beautifully simple.

Instead of 10,000 lockers scattered all over the hallway with 10,000 name stickers, you go to the office and ask for one thing: "Give me 10,000 lockers in a single straight row, side by side, no gaps."

Say your row starts at locker number 5000. Now watch:

The whole trick
student 1's mark → locker 5000
student 2's mark → locker 5001
student 3's mark → locker 5002
…
student n's mark → locker 5000 + n − 1
The teacher types 8437. The computer works out 5000 + 8436 = locker 13436, then opens exactly that locker. One small sum, and you're done.

No name stickers. No searching. The position of a student is now the way to find them. This container, a row of lockers side by side that you find by position, is called an array.

New word · Array A row of memory lockers, side by side, holding values of the same kind. Give it a position number and it hands you that value instantly.

📜
A little historyNobody invented this in a classroom. In the 1950s, programmers did this locker maths by hand, and it was slow and painful. Then in 1957 a language called Fortran said: "just write marks(8437) and I'll do the maths for you." That's the moment the array became part of programming. Real pain, not theory.
New word · Index The index is the position number you use to open an array's locker. One catch: computers count from 0, not 1. So the first mark is marks[0], and the 8,437th mark is marks[8436]. Why start at 0? Because the index really means "how many steps from the start", and the first locker is 0 steps away.

New words · O(1) and O(n) Programmers have nicknames for what you just saw. "Same effort no matter how big" is called O(1) (say it "oh-one"). "Effort grows as the data grows" is called O(n) (say it "oh-en", where n is the number of items). That's all these scary symbols mean. Array jump is O(1). Walking is O(n). You just read your first complexity notation.

A free gift: the neighbours come along

One more real thing, kept simple. Main memory sits far from the computer's brain, like lockers in another building. So when the computer grabs one locker, it photocopies the whole shelf (about 16 lockers) onto a small desk right next to its brain. That desk is called the cache (say it "cash"). Click any locker below:

One shelf of 16 marks · click any locker to read it
Read one mark, and the 15 next to it land on the desk for free. So a loop reading an array flies, the next value is almost always already on the desk.

This only works because array values are neighbours. If your 10,000 values were scattered all over the building, every single read would be another long trip. Keep this in your pocket. It matters a lot when we meet linked lists.

The lockers must be side by side, with no gaps.

The magic sum "5000 + position" only works if every locker is exactly one step from the previous one. If locker 3 could be anywhere in the building, no sum could find it, you'd need a notebook listing where each one went.

So why not just keep that notebook?

Think about what the notebook is: a numbered list where you need to jump to entry n instantly… that's an array again! The escape plan turns out to be the same thing you were escaping. So "side by side" is where the chain stops.

Any locker takes the same time to open, near or far.

Because memory is not a corridor you walk through. It's more like a telephone system: give the number, and the wiring connects you straight to that one locker. Locker 14,999 answers as fast as locker 5,000.

Why is memory wired like a telephone system?

Inside the memory chip there's a circuit called an address decoder. It takes the locker number and electrically switches on exactly that one row, the way dialling a number rings exactly one phone. No walking exists at the hardware level at all. This is why it's called RAM, short for Random Access Memory, where "random" just means ANY locker, equally fast.

Nice. You just crossed into computer architecture without even noticing. This is the bottom floor.

An array can't simply grow bigger when it's full.

Your row got lockers 5000 to 14999. Locker 15000 might already belong to another program's data. You can't grab your neighbour's locker just because you need more space.

Then how do Python lists grow whenever they want?

They secretly cheat: when the row is full, the computer finds a longer empty row somewhere else, copies everything across, and abandons the old row. To avoid doing this often, it books roughly double the space each time. Under every "flexible" list in every language, there is a plain fixed array being replaced when it bursts.

5 Where it hurts · nothing is free

Now watch the array break

The array's power comes from one strict rule: everyone sits in position, side by side, no gaps. Now watch what that rule costs you. Suppose a new value has to go at the front of the row. Nobody can just squeeze in. Every single value has to shift one locker to the right first. Press the button and watch:

Insert 99 at the front · everyone must move
moves so far: 0
7 values → 7 moves, for ONE insertion. Imagine 10 million values, with new ones arriving every second. That's O(n) pain, over and over.

The honest list of array weaknesses:

Adding or removing in the middle

Everyone after that spot has to shift. The closer to the front, the more moves. That's O(n).

Growing bigger

The lockers next to your row might already belong to someone else. To grow, the computer finds a longer empty row elsewhere and copies everything across. O(n) again.

Finding a value (not a position)

"Which student scored 97?" The position tells you nothing about the value inside, so you have to check every locker. O(n).

Reserved empty space

To avoid moving so often, lists quietly rent extra empty lockers. Fast, but a bit wasteful.
Quick check
You need to add new items at the front constantly, and you almost never jump to a position. Is an array a good fit?
Spot onYou'd pay the array's worst cost over and over, and never use its best trick. That mismatch is exactly why the next structure, the linked list, exists.
Think back to the shifting demo you just watched. What did inserting at the front cost? Try again.

The secret of all DSAEvery data structure you'll ever learn exists because the array hurt someone, in one of these exact spots, badly enough that they invented a way around it. Linked lists, stacks, queues, hash maps, trees, each one is a patch for one of these pains. It's not 50 random topics. It's one story.
6 Daily life · you already use arrays

Where arrays hide in your day

Every photo on your phone

A photo is a grid of tiny colour dots (pixels), so it's an array of arrays. "The dot at row 800, column 600" is two little sums away.

Skipping inside a YouTube video

A video is an array of picture frames. Dragging to 12:34 = frames-per-second × seconds = a position. That instant jump is O(1) with your own eyes.

Your Spotify queue

"Play track 7" doesn't listen through tracks 1 to 6 first. It jumps. Position → value.

Every word you read

Text is an array of characters. The first letter of name is name[0].

Excel and marksheets

Rows and columns, arrays of arrays. "Cell C42" is locker maths, twice.

AI models

The "weights" inside ChatGPT-like models are gigantic arrays. GPUs are fast mainly because arrays sit side by side in memory.

The pattern to notice: wherever things have a natural position and you jump straight to it, there's an array underneath.

Coming next: the crack in the wall

You saw how much inserting at the front hurt. So what if your data gets inserted and removed in the middle all the time, and you almost never jump to a position? The array's deal flips completely backwards. The fix lets values live anywhere, with each one holding the address of the next. It's called a linked list, and it's Module 2. You'll get there already knowing why it exists.
7 Practice · now you're ready

Think like an engineer, not an exam-taker

Three real situations. None of them says "use an array". The hints are just questions that lead your own thinking, in the order a senior engineer would ask them. Try to answer each hint in your head before you open the next one. The code comes last, because it's the easy part.

Problem 1 · warm-up
You're building YouTube's video player. A viewer drags the red dot to 12:34 of a 3-hour video. The picture must change instantly, nobody accepts a loading circle in the middle of a drag.
Lead your own thinking
Hint 1 · what is the data?What is a video actually made of? Do those pieces have a natural order?
Hint 2 · what happens most often?In plain words, what does dragging the red dot ask the computer to do? "Jump to any…" what?
Hint 3 · what speed is demanded?"Instant, no matter where they drag", same effort for any position. You learned a nickname for that today.
Hint 4 · what weakness disappears?Frames arrive once, in order, at the end. Nothing is ever inserted in the middle of a finished video. So which array pain simply never happens here?
Discussion

A video is an array of frames. Frames-per-second times 754 seconds gives you the position. One multiplication, one jump, so it's O(1). And because a finished video never inserts frames in the middle, the array's biggest weakness never even fires. Data that gets written once and jumped into forever is the array's perfect customer.

// jump to any moment, instantly
frame = frames[fps * seconds]
show(frame)

Interview extra: a 3-hour video is too big for memory, so real players cut it into chunks and array-jump twice. First to the right chunk, then to the right frame inside it. The same idea, just nested.

Problem 2 · the trap
You work at Instagram. The feed must show newest posts first. Millions of new posts arrive every hour. Your teammate says: "Simple, keep an array, put each new post at position 0." Is that a good idea?
Lead your own thinking
Hint 1 · what is the data?What's the collection here, and what order does the app promise its users?
Hint 2 · what happens most often?Two things happen non-stop. What are they?
Hint 3 · which one is expensive?You watched "insert at the front" a few minutes ago. With 10 million posts stored, what does your teammate's plan cost for EVERY single new post?
Hint 4 · question the assumptionDoes "newest shown first" really force "newest stored at position 0"? Who decided which end of the array is the front?
Hint 5 · the tradeIf you add new posts at the END (cheap, no shifting), what small thing must the reading side do differently?
Discussion

The teammate's plan shifts 10 million posts for every new arrival. That's O(n), happening millions of times an hour. The machine would spend its whole life shuffling. But "front" is just a habit, not a law. Add new posts at the end (no shifting, so O(1)) and just read the array backwards. The user sees exactly the same feed. The cost simply vanishes. Not with a fancy structure, but by questioning one assumption.

// writing: cheap
posts.append(new_post)
// reading: newest first, free
for i from last position down to 0:
    show(posts[i])

Interview extra: this "only ever add at the end" idea, at giant scale, is called an append-only log. It's the heart of how big systems like Kafka and databases record events. You just reasoned your way to it.

Problem 3 · the clever swap
You're building Spotify's shuffle. Every song must play exactly once, in random order, and pressing "next" must be instant, even with 10,000 songs.
Lead your own thinking
Hint 1 · what is the data?What's the collection, and what does "exactly once" forbid you from doing?
Hint 2 · try the lazy plan"Pick any random song; if it already played, pick again." Feels fine at the start. What happens when only 1 song out of 10,000 is left unplayed?
Hint 3 · find the real problemThe hard part is remembering who played. What if the array itself could keep played songs physically separate from unplayed ones?
Hint 4 · the moveYou're allowed to rearrange. What single cheap operation could push a just-played song out of the "unplayed" zone?
Hint 5 · the tradeSwapping scrambles your nice ordered playlist. Does that matter? Could you shuffle something else instead of the songs themselves?
Discussion

The lazy plan dies at the end. With one unplayed song left, you're rolling the dice about 10,000 times hoping to hit it. The neat fix: keep all unplayed songs in positions 0 to k. Pick one at random, swap it to position k, then shrink k by one. The wall between "unplayed" and "played" is just a number. Every "next" costs exactly one swap. Instant, forever.

k = number of songs - 1
when user presses next:
    r = random position from 0 to k
    swap(songs[r], songs[k])
    k = k - 1
    play songs[k + 1]

Interview extra: you just re-invented the Fisher-Yates shuffle, an algorithm most people memorize from a book. You didn't memorize it. The costs cornered you into it. That's the whole difference this course is built on. (And real players shuffle a copy of the position numbers, keeping your playlist order safe.)

8 Now code it · interview-style problems

Solve real problems, with a method that fits any problem

The scenarios above taught you when to reach for an array. Now let's learn to solve array coding problems, the LeetCode kind that show up in interviews. We're not here to memorize answers. We're here to build one method you can point at any problem you've never seen before.

🧠
Use this on every problem, foreverSame five steps, whether it's your first array problem or a hard graph one in month two. The steps never change. Only the problem does.
Understand itSay the problem back in your own words. What comes in, what goes out, and what edge cases exist (empty input? all zeros? one item?).
Brute force firstWrite the dumb, slow way that definitely works. Never skip this. A slow answer beats a blank page, and it shows you the shape of the problem.
Find the wasteLook at your brute force. Where does it redo work it already did? That wasted work is almost always where the faster idea is hiding.
Pseudo-code itWrite the steps in plain language, no syntax. If you can't say it in plain steps, you don't understand it yet. This part is the real thinking.
Code it, then cost itTurn the pseudo-code into real code. Then say its time and space cost out loud, in O() terms. Interviewers always ask.

Try each problem yourself first. Open each step only after you've had a real go. That struggle is where the learning actually happens.

Easy · warm-upLeetCode 1480 · Running Sum of 1d Array

Given a list of numbers, return a new list where position i holds the sum of every number from the start up to i.

Example: [1, 2, 3, 4] becomes [1, 3, 6, 10]  (1, then 1+2, then 1+2+3, then 1+2+3+4)

Step 1 · Understand it

Input: a list of numbers. Output: a list of the same length, where each spot is the "total so far". One edge case to remember: an empty list should just give back an empty list.

Step 2 · Brute force first

For each position i, walk from the start and add up everything up to i. It works. But to fill position 9999, you re-add positions 0 through 9999 from scratch, and you do that for every single position.

Pseudo-code · brute force
for i from 0 to last:
    total = 0
    for j from 0 to i:
        total = total + nums[j]
    out[i] = total

A loop inside a loop, so the cost is O(n²). On a big list, that's painfully slow.

Step 3 · Find the waste

Look at what the brute force throws away. To get the total at position i, it re-adds everything from 0 to i. But the total at position i is just the total at position i minus 1, plus one more number. We already had that total a moment ago, and we threw it away.

So carry a running total as you walk, and just add the current number to it. One pass, no re-adding.

Step 4 · Pseudo-code the good idea
Pseudo-code · one pass
running = 0
for each number x in nums:
    running = running + x
    add running to the output list
return output list
Step 5 · Code it, then cost it
C++
vector<int> runningSum(vector<int>& nums) {
    int total = 0;
    vector<int> out;
    for (int x : nums) {
        total += x;
        out.push_back(total);
    }
    return out;
}

Time: O(n), one clean pass. Space: O(n) for the output list (or O(1) extra if you're allowed to overwrite the input in place).

Connects to: this "reuse the previous total" trick is the seed of prefix sums, a whole topic later in the course. You just met it early.

Easy → MediumLeetCode 283 · Move Zeroes

Move every 0 to the end of the list, while keeping the order of the non-zero numbers. Do it in place, without building a second list.

Example: [0, 1, 0, 3, 12] becomes [1, 3, 12, 0, 0]

Step 1 · Understand it

Same list, rearranged: non-zeros stay in their original order, all the zeros get pushed to the back, and we're not allowed to make a new list. Edge cases: a list with no zeros (leave it alone), a list of all zeros, and an empty list.

Step 2 · Brute force first

Make a new list. Walk the input and copy over every non-zero. Then add enough zeros at the end to fill it up. It works and it's easy to picture.

The catch: the problem said in place, no second list. So this passes the logic test but breaks the rules. Good. Now we know exactly what we have to beat.

Step 3 · Find the waste (and the trick)

Remember the Spotify shuffle? You kept a wall between "done" and "not done", and the wall was just a number. Same idea here.

Keep a write pointer for where the next non-zero belongs. Walk a read pointer across the whole list. Every time read finds a non-zero, swap it to the write spot and push write forward one. When you're done, every non-zero sits packed at the front in order, and the zeros are automatically left at the back.

Step 4 · Pseudo-code the good idea
Pseudo-code · two pointers
write = 0
for read from 0 to last:
    if nums[read] is not 0:
        swap nums[write] and nums[read]
        write = write + 1
Step 5 · Code it, then cost it
C++
void moveZeroes(vector<int>& nums) {
    int write = 0;
    for (int read = 0; read < nums.size(); read++) {
        if (nums[read] != 0) {
            swap(nums[write], nums[read]);
            write++;
        }
    }
}

Time: O(n), one pass. Space: O(1), no second list, just two little pointers.

Connects to: this "one wall, two pointers" pattern is a named Week 1 technique called two pointers. You've now seen it twice (Spotify, and here). That's not a coincidence. The same handful of patterns keep coming back.
